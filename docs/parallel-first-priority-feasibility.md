# 双 Edge 第一优先级并发可行性验证

验证日期：2026-09-22（Asia/Shanghai）

## 结论

双 Edge 并发控制可行。“同账号同毫秒双提交”只成功一笔，而让 B 相对 A 延迟
150 ms 的单次实测成功预约了两个时段。正式实现应使用两套长期保留的独立 Edge
profile，不能在每天
06:57 临时创建空 profile。两套普通 Edge 根进程可以同时登录同一个复旦账号、
同时打开资源 1055、近乎同时刷新，并分别保持两个不同时段的选择。

Playwright 和 Selenium 不适合控制 booking 页面。两者会启用浏览器 Debugger 域，
触发该页面的反调试暂停。可行的控制方式是直接连接两个不同的本地 CDP 端口，
仅使用导航、JavaScript 执行和网络观察命令，不启用 Debugger 域。

## 本机条件

- macOS 26.2（25C56）
- Microsoft Edge 153.0.4234.48
- 24 GiB 内存
- 验证时数据卷剩余约 206 GiB
- 两个实验 profile 合计曾占用约 738 MiB，实验结束后已删除

本机可以同时运行两个具有不同 `--user-data-dir` 和不同调试端口的 Edge 根进程。
成功验证中两边的根 PID、profile 目录和调试端口均不同。

## 网站实测

目标日期为 2026-09-24，两个时段为 08:00–09:00 和 09:00–10:00。先完成了不提交的
并发选择验证，再经用户明确授权完成一次真实双提交。

完成了两次全链路成功验证：

| 指标 | 第一次 | 第二次 |
| --- | ---: | ---: |
| 两个刷新开始时间差 | 0 ms | 1 ms |
| Edge A 选中耗时 | 18 ms | 20 ms |
| Edge B 选中耗时 | 18 ms | 129 ms |
| Edge A `/resource/launch` 请求 | 0 | 0 |
| Edge B `/resource/launch` 请求 | 0 | 0 |

两次成功验证均满足：

- 两个 Edge 同时持有不同目标时段的选择；
- 两边各有 12 个复旦域 Cookie；
- 两边 `navigator.webdriver` 均为 `false`；
- 目标格子均显示“可预约”且具有可点击状态；
- 未观察到任何预约提交请求。

同账号并发登录没有导致另一会话退出或预约表失效。空 profile 的统一认证页面偶尔
停留在失效的二维码视图、未生成账号密码表单，因此“每次从零登录”存在波动。这是
认证前端首载问题，不是双进程或 booking 页面拒绝并发；已有多轮中两个会话都成功
到达预约表。正式实现应预先初始化并长期保留两个 profile，在 06:57 只做登录态续期。

## 正式实现约束

1. 使用 `.state/edge-profile-a` 和 `.state/edge-profile-b`，权限设为仅当前用户可读写。
2. 各自启动一个普通 Edge 根进程和一个独立本地 CDP 端口，并关闭后台窗口节流。
3. 06:57 并发进入资源页，只有两边都到达完整预约表后才进入就绪状态。
4. 07:00 用同一个释放时间屏障同时刷新；两路分别执行原“第一优先级”的选择与提交。
5. 每路最多发送一次 `/reservation/site/resource/launch`；若继续研究双提交，应测试小幅
   错峰，不能因某一路结果不明确而自动重试。
6. 分别记录刷新、选中、提交和结果时间；结果不明确时只查询“我的预约”，不盲目重试。

## 真实双提交结果

2026-09-22 17:48:26，两路点击开始时间差为 0 ms。两个 Edge 各发送一次
`/reservation/site/resource/launch`，两份 HTTP 响应状态均为 200，没有重复请求。

“我的预约”最终只出现一条本轮有效记录：2026-09-24 08:00–09:00，2号场地，状态为
“已预约”。09:00–10:00 没有出现本轮记录。历史列表中存在同一天这两个时段此前串行
预约成功后取消的记录，因此账号能够持有两个相邻时段；本轮失败更可能是两笔完全同时
提交产生的服务端竞争或业务层拒绝。由于没有保存第二路响应正文，不能进一步确定具体
错误码。

结论是：双进程可以把两笔请求同时送达，但 0 ms 双提交不可靠，不应直接用于正式抢场。

## 150 ms 错峰双提交结果

2026-09-22 18:11:29，A 先提交 08:00–09:00，B 按配置延迟 150 ms 提交
09:00–10:00，实际点击开始时间差为 155 ms。两路各发送一次提交请求，HTTP 状态均为
200，响应正文均为 `e: "OK"`，返回预约 ID `925146` 和 `925147`。“我的预约”自动核验
结果为 `[true, true]`。

本轮还验证了从现有 CourtScript 专用 profile 创建两份临时隔离副本：两边分别在约
5.6 秒和 6.3 秒内进入预约表，明显避开了空 profile 统一认证页的随机首载失败。实验完成
后两份临时副本均已删除。

本次成功说明 150 ms 错峰是可用候选值。每路仍须严格限制为一次提交，并保存业务响应
正文。测试结束后，两个新预约均已按授权取消；复核两个时段均无活动预约。

2026-09-22 18:24:18 又重复了一次同参数真实测试：刷新开始时间差为 2 ms，实际提交
间隔为 152 ms。两路仍各只有一次请求，HTTP 200 且业务响应均为 `e: "OK"`，返回预约
ID `925150` 和 `925151`，“我的预约”核验再次为 `[true, true]`。测试完成后两条记录也
已取消，并复核为无活动预约。

因此 150 ms 错峰已经连续两轮成功，可信度明显高于 0 ms 同时提交。不过，这两轮发生在
资源已经开放且仍有余量的时段，尚未覆盖早上 07:00 高竞争场景；正式使用前仍应保留精确
时段检查、双路一次提交限制和完整业务响应日志。
